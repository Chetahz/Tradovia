# Tradovia V34.6 → Production Fidelity Audit

Audit baseline: Original Prototype `index.html` at blob `fec45e9a6c8ae5e38f00f3442479bc243315f869`, compared with `production/` on `phase-1/production-foundation` at commit `fdea626`.

This document is a preservation contract. A production implementation may change architecture, but it must not silently remove an approved product surface, workflow, state, sample, or mobile behavior from V34.6.

## Classification

- **Preserved** — the production route and core workflow exist.
- **Missing** — the approved prototype capability is absent from production.
- **Changed** — a related surface exists, but content, behavior, scope, or hierarchy differs materially.
- **Needs polish** — functionally present, but fidelity, responsiveness, localization, accessibility, or validation is incomplete.

## Restoration milestones

### F1 — Truthful demo and data-source separation

Restore an explicit Demo Portfolio and Sample Data system. Demo data must be isolated from user/local records, visibly labeled at page and metric level, and removable/switchable without deleting user data.

**Checkpoint F1.1:** Implemented a read-only Demo Portfolio dataset, a persistent Demo/My Portfolio selector, automatic protection of existing local records, and explicit `demo`/`manual` source identities. Demo records are returned in memory and are never written into user storage. Imported and MT5 source types are reserved in the model but no live connection is enabled.

### F2 — Workspace feature parity

Restore journal dimensions and filters, Edge Engine, Reports, Risk Center, Position Size, Market Sessions, Settings/export, and the fuller Playbook and Goals models. Preserve current CRUD and calculations throughout.

**Checkpoint F2.1:** Restored a denser dashboard hierarchy with explicit Demo Portfolio disclosure, portfolio context, derived outcome totals, a cumulative recorded-P&L visualization, recent activity, and Result → Why → Action review. All displayed figures are derived from the active dataset; demo figures remain visibly marked as Sample Data.

### F3 — Landing and authentication presentation parity

Restore approved V34.6 landing content, pricing interactions, FAQ, motion, complete EN/TH behavior and the separate themed authentication surfaces. Authentication remains explicitly disconnected until infrastructure work begins.

### F4 — Market-context parity

Restore TradingView shell, ticker, watchlist and technical summary. Add Economic Calendar and Market News only with a verified provider, or show a visibly marked sample state with no “live” claim.

### F5 — Product fidelity QA checkpoint

Founder review against V34.6 on desktop and representative iOS/Android sizes. Resolve regressions before starting production infrastructure.

### I1 — Production infrastructure

Database → Authentication → Storage → Portfolio/Trading Accounts → Subscription/Payments → Security hardening. Use migrations and per-user authorization; do not treat local storage or demo data as production records.

## Non-regression gates

1. Original `index.html` remains an immutable visual/functional reference.
2. Demo, sample, user-entered and provider-sourced data must have distinct identities.
3. No feature is removed or renamed out of the information architecture without Founder approval.
4. Every frontend milestone covers desktop and real iOS/Android usability.
5. Typecheck, lint and production build must pass before a milestone preview.
6. Deployment changes are batched by milestone.
7. No merge to `main` and no Production deployment without Founder approval.
